Triton kernel 入门

写第一个 kernel：从 copy 开始

这份教程的目标不是让你会写 copy，而是让你建立三件事：执行模型的直觉、验证的方法、测量的纪律。后面 03–08 都用同一套东西。

01先建立执行模型

Triton 里你写的函数不是"一个线程干什么"，而是"一个 program 干什么"。

你写一个 kernel，然后告诉它要开多少个 program（这就是 grid）。每个 program 拿到一个编号 pid，自己去数组里认领一段活。所有 program 同时跑。

所以写任何一个 kernel，先回答两个问题：

  • 整个问题要切成几份？→ 决定 grid
  • 每一份多大？→ 决定 BLOCK
和 CUDA 最大的区别：你没有 threadIdx、没有 warp、没有共享内存声明。tl.arange(0, BLOCK) 生成的是一整个向量，不是循环。你写的是"这批数据"，编译器决定怎么摊到 128 个线程上。

02六行代码，逐行拆

copy 的完整实现就是下面这个。其中 4 行是固定的套路，只有 BLOCK 是你要调的。

@triton.jit
def copy_kernel(x_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid  = tl.program_id(0)                      # 我是第几个 program
    offs = pid * BLOCK + tl.arange(0, BLOCK)     # 我负责哪一段
    mask = offs < n                              # 越界的 lane 屏蔽掉
    v    = tl.load(x_ptr + offs, mask=mask)      # 一次搬整段
    tl.store(out_ptr + offs, v, mask=mask)       # 一次写回去


def run(x, out):
    n = x.numel()
    grid = (triton.cdiv(n, 4096),)
    copy_kernel[grid](x, out, n, BLOCK=4096)
行在干什么错了会怎样
program_id(0)取第 0 维的 program 编号二维 grid 时要 (0) 和 (1) 两个
pid * BLOCK本段的起点（全局下标）忘了乘 BLOCK，所有 program 都抢开头一小段
tl.arange(0, BLOCK)段内偏移向量 [0,1,...,BLOCK-1]不能是变量，必须是编译期常量
mask = offs < n标记哪些 lane 是真实数据漏了 → 越界读写，可能不报错但结果错
cdiv(n, BLOCK)向上取整算 program 数用整除 → 尾巴那一段永远没人处理
最容易犯的三个错，按踩坑频率排：
1. grid 用了整除而不是 cdiv —— 数组尾部少算一截，结果看起来"大部分对"。
2. 忘了 mask —— 越界访问。GPU 不保证报错，可能给你一堆垃圾值。
3. 把 n 写成了 shape 的第一维 —— 二维张量要用 numel()，显存里是平铺的。

03验证：先对，再快

顺序不能反。一个跑得飞快的错误 kernel 毫无价值。

# 1. 正确性
check.py --only 02_copy

# 2. 换个别扭的尺寸再验一遍
check.py --only 02_copy --odd

# 3. 调参
tune_copy.py
为什么必须有第 2 步：常规 shape 会放过整除 bug。
题库固定是 (4096, 1024)，总元素 4,194,304 恰好能被 BLOCK=4096 整除。 所以 grid = (n // 4096,) 这种错写法也能"通过"——余数为 0，尾部根本不存在。 实测换成别的尺寸立刻露：n=1,000,000 漏 576 个元素，n=1,000 时 grid=0， 整个 kernel 都没启动，却依然不报错。
--odd 会用 (997, 1024)、(1003, 512)、(1, 4096) 这几组尺寸重验； --odd hard 再加 (333, 1000)、(77, 127)，把 N 也变成非 2 的幂——归约类 kernel 必须自己做 next_power_of_2 + mask 才能过。

正确性那一关框架会替你比（torch.allclose）。通过之后才看性能数字。第一次跑通的输出：

02_copy       通过          0.1893     177.2    98.2%       1       1

四列分别是：耗时、带宽、占峰值百分比、启动了 1 次 kernel（理想 1 次）。最后一组数字是重点——它直接告诉你走了几趟访存。

凡是正常配置，全是 180 GB/s 左右。掉下去只有一个原因：给太少线程扛太多元素。

判断方法是看"元素/线程"这一列：BLOCK / (num_warps × 32)。超过 128 就开始掉，到 512 直接腰斩再腰斩。因为每个线程要串行处理太多次，一次 load 的延迟还没藏住，下一次又来了。

所以 elementwise kernel 没有优化空间。这不是你写得不好，是它本来就贴着 roofline。你随手写的 BLOCK=4096, num_warps=4 就已经到 100% 了——PyTorch 自己的 copy_ 是 179.4 GB/s，你打平了。

顺便验证了一个常见猜疑：去掉 mask 有没有用？没有。

8192180.0180.00.0

原因是访存已经完全饱和，那点比较指令被藏在访存空隙里。这就是 roofline 的意义：先确认瓶颈在哪，再去优化那个东西。在访存受限的 kernel 上抠指令数，纯属白费力气。

05一个我亲自踩过的测量陷阱

第一版扫参，一半配置测出来是 18 GB/s，我差点写成"某些配置慢 10 倍"。

真相是：@triton.jit 的第一次调用包含编译，要几百毫秒到几秒。我的预热是「跑满 0.7 秒」，结果编译把 0.7 秒全吃光了，GPU 从头到尾在搬数据、人还没开始计时——但显存时钟还停在待机频率，于是测出 18 GB/s。

修法是：第一次调用单独跑一次，排除在预热和计时之外。改完同一个配置从 18 变成 180.7。

这条对你有两层用：

  • 自己写测量脚本时，必须先做一次 warmup 调用把编译挡掉。
  • 看到"某个配置异常慢"的第一反应，应该是怀疑测量，而不是相信结论。

06想知道编译器到底干了什么

不用猜，PTX 就在编译产物里。

k = copy_kernel.warmup(x, out, n, BLOCK=2048, num_warps=4, grid=(1,))
print(k.asm["ptx"])          # 里面有 ld.global / st.global

看 load 的宽度就够了：

元素/线程生成的指令含义
≥ 4ld.global.v4.b32128 位向量化，一次搬 4 个 float
2ld.global.v2.b3264 位，一次 2 个
1ld.global.b32标量，一次 1 个 float

这条对你后面写 08_transpose 极其关键：那个 kernel 的问题就出在某一边的访存宽度掉到标量、而且不连续，此时带宽会掉到 1/8。

顺带一个坑：@triton.jit 的函数必须在真实 .py 文件里。写进 REPL、python -c、或者 stdin 管道都会报 @jit functions should be defined in a Python file——因为 Triton 要读源码做 AST 分析。

07API 速查

要干的事写法
取 program 编号tl.program_id(0) / (1)
生成偏移向量tl.arange(0, BLOCK)
读显存tl.load(ptr + offs, mask=..., other=0.0)
写显存tl.store(ptr + offs, v, mask=...)
降维归约tl.sum(v, axis=0) / tl.max(v, axis=1)
前缀和tl.cumsum(v, axis=1)
交换维度布局tl.trans(v)
编译期常量参数BLOCK: tl.constexpr
启动时指定线程数kernel[grid](..., num_warps=4)
向上取整triton.cdiv(n, BLOCK)

08现在该干什么

copy 已经能跑了，它现在的角色是尺子。从下一题开始，你自己写，写完全部丢给 check.py。

  • 01_add：多一个 tl.load，其他一模一样。五分钟的事。
  • 03_sum / 04_max：开始有意思了。tl.sum(v, axis=0) 把 BLOCK 压成一个数。真正的取舍是"一个 program 处理一行"还是"处理多行"——4096 个 program 抢 20 个 SM，你想想够不够。
  • 06_softmax：本组重点。朴素三趟读，一行装得进寄存器就只要一趟。
  • 08_transpose：回头看第 06 节的向量化表，这题就是围绕它出的。

判断标准始终是两个数：占峰值百分比，和启动次数 vs 理想次数。

实测数据来自本机 RTX 3050 Ti Laptop（sm_86 / 4GB / 20 SM），torch 2.11.0+cu128，Triton 3.8.0，2026-10-18。峰值带宽取实测值 180.5 GB/s，所以个别配置会显示 100.6%，属正常浮动。
