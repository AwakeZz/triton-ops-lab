# triton-ops-lab

从零手写的 Triton GPU kernel 练习集。12 道题：前 8 道覆盖 elementwise、reduction、scan、
归一化和转置，用 roofline 带宽模型验收；后 4 道是 GEMM 的四级台阶，用 fp16 tensor core
峰值验收，最后一版超过 cuBLAS 11%。

每一题都不是"能跑就算完"，而是问一句：**它离这张卡的硬件上限还有多远，中间那段差距是哪来的。**

## 硬件基线

| 项 | 值 |
|---|---|
| GPU | NVIDIA RTX 3050 Ti Laptop (sm_86, 20 SM, 4 GB, L2 2 MB) |
| 理论带宽 | 192 GB/s |
| 实测带宽 | 180.5 GB/s（94%） |
| FP32 峰值 | 8.2 TFLOPS |
| fp16 tensor core 实测 | 18.2 TFLOPS（规格 40.7，笔记本 45 W 功耗墙吃掉 55%） |
| roofline 平衡点 | 45.4 FLOP/Byte（FP32 峰值 ÷ 实测带宽） |

访存类的目标是把带宽压到 180 GB/s 附近；GEMM 类的目标是逼近 18.2 TFLOPS。
两套分母都是实测量出来的，不是规格表上的数字 —— 换一张卡就得先跑 `bench_baseline.py`。

## 验收结果

2026-10-29 完整跑一遍，12/12 通过。

### 访存类 8 题（分母 = 180.5 GB/s）

| # | kernel | ms | GB/s | % 峰值 | 启动次数 |
|---|---|---|---|---|---|
| 01 | vector add | 0.2804 | 179.5 | 99.4% | 1 |
| 02 | copy | 0.1886 | 177.9 | 98.5% | 1 |
| 03 | row sum | 0.0932 | 180.2 | 99.8% | 1 |
| 04 | row max | 0.0932 | 180.2 | 99.8% | 1 |
| 05 | row cumsum | 0.1874 | 179.1 | 99.2% | 1 |
| 06 | row softmax | 0.1874 | 179.1 | 99.2% | 1 |
| 07 | layernorm | 0.1874 | 179.1 | 99.2% | 1 |
| 08 | transpose | 0.1902 | 176.4 | 97.7% | 1 |

"启动次数"由 monkey-patch `JITFunction.run` 统计，等价于**访存趟数**。8 个 kernel
全是 1 趟，说明没有一个是"读一遍求 max、再读一遍求 sum"的朴素实现。

### GEMM 4 题（分母 = 18.2 TFLOPS，1024³ fp16）

| # | 版本 | ms | TFLOPS | % 峰值 | 相对 09 |
|---|---|---|---|---|---|
| 09 | 朴素：一 program 一元素，K 串行 | 462.15 | 0.0046 | 0.0% | 1× |
| 10 | 分块 + 3D 外积求和（纯 FMA） | 0.7240 | 2.97 | 16.3% | **638×** |
| 11 | `tl.dot`（tensor core） | 0.1369 | 15.69 | 86.2% | **3376×** |
| 12 | 软件流水 `num_stages=3` | 0.1335 | 16.08 | 88.4% | **3462×** |

第 09 题是故意写得最慢的，它唯一的作用是当分母：一个 program 算一个输出元素，
K 维 1024 个数串行循环，零复用。三个版本的加速比都相对它。

## GEMM 四版，每一步快在哪

**09 → 10（638 倍）：tile 化。**
原来每个输出元素都要把 K 维的 A 行和 B 列各读一遍，总共 `M·N·K` 次元素读。
分块之后，一份 A 块被 BN 个输出复用、一份 B 块被 BM 个复用，访存降到
`(BM+BN)/(BM·BN)` 的量级。638 倍全从这笔账来。

**10 → 11（5.3 倍）：`tl.dot`。**
第 10 题那行 `tl.sum(a[:, :, None] * b[None, :, :], 1)` 是"在寄存器里把乘积展开成 3D 张量
再沿 BK 归约"，纯 FMA。换成 `tl.dot` 后，mma 指令在硬件内部复用操作数，不再付这份
layout 转换的账。代价是三个硬约束：输入必须 fp16/bf16、三维都要 ≥16、累加器要用
`acc = tl.dot(a, b, acc)` 三参形式传进去。

**11 → 12（+2%）：软件流水。**
`num_stages=1` 的 PTX 里 `cp.async` 是 **0 条**，走同步 `ld.global` —— 搬第 k 块数据的
时候 tensor core 在闲着。`num_stages=3` 变成 12 条 `cp.async`，第 k+1 块的搬运和第 k 块的
mma 重叠。只有 2% 的边际，因为 11 题已经把 86% 拿到了；这题的价值在 PTX 证据链，
不在那个百分数。

## 与 PyTorch / cuBLAS 对照

| 算子 | 本仓库 | 参考实现 | 差距 |
|---|---|---|---|
| copy (256 MB) | 180.5 | 179.4 `copy_` | 打平 |
| add | 179.4 | 179.7 `x + y` | 打平 |
| transpose 4096×1024 | 176.4 | 102.0 `x.t().contiguous()` | **1.73×** |
| cumsum (N=8192) | 178.8 | 132.7 `torch.cumsum` | **1.35×** |
| **GEMM 1024³ fp16 (11)** | **15.69 TF** | 14.46 cuBLAS | **1.09×** |
| **GEMM 1024³ fp16 (12)** | **16.08 TF** | 14.46 cuBLAS | **1.11×** |

elementwise 已经贴着 roofline，没有优化空间；能明显超过参考实现的是
**一边访存不连续**的算子（转置、长行扫描）和**能绕开 layout 转换**的 GEMM。

## 12 道题

| # | 算子 | 难点 |
|---|---|---|
| 01 | `out = x + y` | 一维 grid、尾块 mask，算术强度 0.25 |
| 02 | `out = x` | 尺子：后面每题都拿它比 |
| 03 | `out[i] = sum(x[i, :])` | 一 program 一行还是多行 |
| 04 | `out[i] = max(x[i, :])` | 和 03 同构，换 `tl.max`，`other` 必须是 `-inf` |
| 05 | `out[i, :] = cumsum(x[i, :])` | 前缀和跨 block 有依赖 |
| 06 | `softmax(x[i, :])` | online 递推，能否一趟做完 |
| 07 | `layernorm` | mean 和 var 必须同一趟算出 |
| 08 | `x.T` contiguous | 读和写必有一边不连续 |
| 09 | `C = A @ B` 朴素 | 三个下标步长，理解为什么慢 |
| 10 | 分块（不用 dot） | 复用怎么从 tile 里长出来 |
| 11 | `tl.dot` | 输入 dtype、最小尺寸、累加器形式 |
| 12 | 流水线 + 调参 | `num_stages` 的真实语义、tile 无全局最优 |

## 几个反直觉的实测结论

这些结论都是在同一张卡上扫参跑出来的，有几条推翻了我最初的猜测：

1. **elementwise 没有优化空间。** copy 扫了 28 种 `BLOCK × num_warps` 组合，
   正常组合全部落在 180 GB/s，只有"每线程元素 > 128"开始掉
   （8192 元素 / 1 warp 只有 145.1）。调参是在做无用功。

2. **多行合并对带宽零收益。** row sum 从 `BLOCK_N = N/8` 到 `4N`、一 program
   处理 1~16 行，12 种配置全部 180.2 GB/s。原本以为多行能提升 ILP，实测否定。

3. **但 N < 32 时必须合并。** N=16 时一行一个 program 只有 30.1 GB/s
   （一个 warp 的 32 个 lane 填不满），合并 16 行才回到 178.3。
   分块方式要不要改，取决于 N 而不是数据总量。

4. **`mask` 的开销可以忽略。** 带 mask 与不带 mask 的 copy 都是 177.4 GB/s ——
   PTX 里只是给 `st.global` 加了个 `@%p` 谓词。不要为省 mask 冒越界的风险。

5. **`tl.trans` 不影响性能。** 转置 32×32 加不加 `tl.trans` 都是 176~179 GB/s，
   Triton 3.8 的 layout 优化自己会处理。它的作用是让值的 shape 与写地址矩阵对齐，
   属语义需要。性能来自 tile 化本身：1D + `div/mod` 的朴素散写只有 65.8 GB/s。

6. **`other` 填错不会报错。** `tl.load(ptr, mask)` 省略 `other` 就是默认填 0。
   对 sum 恰好正确（0 是单位元），对 max 就致命（全负行返回 0）。统一显式写。

7. **`.to(tl.float32)` 喂给 `tl.dot` 不报错，静默降级成 TF32。** fp16 输入的 mma 是
   `m16n8k16`（K=16/次），一转 float32 就变成 `m16n8k8`（TF32，K 减半）。
   同一个 kernel 只差这一处：14.36 → 7.85 TFLOPS。第 10 题必须转（fp16 乘积会舍入，
   1024 项累下来误差 3.5e-2），第 11 题必须不转（mma 内部乘积是精确的）。
   **同一个问题在不同 kernel 里答案相反。**

8. **tile 尺寸没有全局最优，它和 M/N 绑死。** 三种尺寸实测：

   | 尺寸 | 32/32/32 | 64/64/32 | 128/128/32 | 最优 |
   |---|---|---|---|---|
   | 1024³ | 12.38 | **15.20** | 12.19 | 64 |
   | 2048³ | 12.23 | 11.94 | **15.97** | ≥128 |
   | 4096³ | 6.00 | 11.38 | **16.15** | ≥128 |

   原因是两个力方向相反：tile 越大，block 数越少（1024³ 下 128×128 只有 64 个 block，
   20 个 SM 要跑 4 轮，尾轮只有 4 个 SM 有活）；tile 越小，每个 FLOP 要搬的数据越多
   （算术强度 `BM·BN/(BM+BN)` 从 64 掉到 16）。小矩阵怕前者，大矩阵怕后者。

9. **`num_stages=N` 只给 N-1 块 shared buffer。** 实测 smem：s1=8 KB、s2=8 KB、
   s3=16 KB、s4=24 KB。所以 s2 和 s1 一样慢（14.27 vs 14.31）—— 名义两级，物理上
   只有一块 buffer，"边读边算"根本没有第二个位置。s4 掉下来也不是因为 barrier 变多，
   是 `floor(102400/24576)=4`，每 SM 的 CTA 从 5 掉到 4。

10. **shared memory 带宽从来不是瓶颈。** 每 FLOP 只要 `(BM+BN)/(BM·BN)` 字节的 smem 读，
    128/128 是 0.0156 B/FLOP，跑到 16 TFLOPS 也只占 smem 带宽的 5.8%（smem 是 4.34 TB/s，
    HBM 只有 0.18 TB/s，差 24 倍）。真正卡 occupancy 的是**寄存器**：128/128 用 167 个，
    每个 SM 只放得下 1 个 CTA。tile 的意义就是把慢带宽换成快带宽，不是"把 smem 用满"。

11. **同一个进程里连测多个配置不可信。** 同一个 kernel、同一个配置，在扫参脚本里测出
    0.39 TFLOPS，独立进程重测是 3.17，差 8 倍。现在所有配置都**一配置一进程、各跑 3 轮**
    （min/max 差 <0.5%）。同理：探针口径和 `check.py` 口径差 8~9%（探针每次 launch 都
    synchronize），**横向比配置用探针，报成绩用 check.py**。

## 快速开始

```bash
pip install torch triton
python bench_baseline.py         # 先把自己的卡量一遍，基线因卡而异
python check.py                  # 跑全部 12 题
python check.py --only 11_gemm_dot
python check.py --odd            # 加测非常规尺寸
python check.py --odd hard       # 再加"非 2 的幂"尺寸
```

`PEAK_GBPS = 180.5` 和 `PEAK_TFLOPS_TC = 18.2` 写在 `check.py` 里，换卡需要先跑
`bench_baseline.py` 改这两个数。

`--odd` 是这套框架的关键设计。常规尺寸 (4096, 1024) 恰好都是 2 的幂，
`grid` 写成整除也能通过；非常规尺寸专门用来抓"只在特定 shape 正确"的错：

| 级别 | 尺寸 | 抓什么 |
|---|---|---|
| `--odd` | (997,1024) (1003,512) (1,4096) | grid 用整除、尾部 mask 没盖住 |
| `--odd hard` | 追加 (333,1000) (77,127) | BLOCK 假设了 N 是 2 的幂 |

GEMM 题的 `--odd` 用的是 `(1000,1000,1024)` `(2048,512,768)` 这类 N≠K 的三元组 ——
`A` 的行距是 K、`B` 的行距是 N，写成同一个值在 1024³ 下会**碰巧通过**。

## 验收框架做的三件普通 benchmark 不做的事

1. **统计 kernel 启动次数**：`launch` 与 `ideal_launch` 并排打印。多一次启动 =
   多一趟访存 = 可直接量化的优化空间。

2. **按单次耗时反推预热次数**：笔记本 GPU 有频率阶梯，测太短会低估一个数量级。
   这里踩过最大的一个坑：原来写的是"跑满 0.8 秒墙钟再 synchronize"，但 `launch` 是
   异步的，一个 462 ms 的朴素 GEMM 会在 0.8 秒里被塞进上千次。现在先测一次单次耗时，
   预热次数 = 800 ms ÷ 单次，上限 4000。

3. **反直觉的数字必须重跑。** 这套框架早期报过四次假数据：22 GB/s 的 layernorm、
   13.4 GB/s 的转置、32.2 GB/s 的 `torch.add` —— 全部是"第一次调用还在编译、GPU 还在
   待机频率"造成的，重跑即恢复 179~180。现在凡是偏离预期的数，一律独立进程重跑两次。
